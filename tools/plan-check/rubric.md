# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| cause-fits-evidence | The plan's stated cause (its diagnosis), read against every step and every control run in the repro evidence block, and against any cause explanation a maintainer gave in the thread highlights | Every control run in the repro evidence comes out the way it would if the plan's stated cause were true. Fails if any control rules the stated cause out (for example, the same input works while the blamed component is still in the path, or the evidence shows the damage happening before or outside the code the plan blames), or if the plan waves away shown evidence as irrelevant without explaining it. A plan that adopts the issue's or the thread's cause passes only if the repro evidence also fits that cause | required |
| fix-targets-cause | The plan's change (approach section or proposed changes), read against the cause the repro evidence pins down | The change modifies the code or behavior that produces the bug, so the repro's failing step would stop failing without the user doing anything different. Fails if the plan only documents a workaround, hides the failure (for example, a catch-all recover or try/except around it), or patches a different layer than the one the evidence points at. Deliberately fixing a smaller part of the bug and naming what is deferred is fine | required |
| one-bounded-change | The plan's scope statement, its list of files or areas, and its numbered changes, read against what the issue asks for | Every change in the plan is needed to fix this issue, plus regression tests for it. Fails if the plan adds work the issue did not ask for: dependency migrations or upgrades, new user-facing options or settings, refactors or module restructures, rewrites of a subsystem, CI additions beyond a test for this bug, or fixes for other issues "while in the area", even when the core fix inside it is correct. Saying that something is out of scope, deferring it, filing it separately, or only noting it for reviewers is not scope creep | required |
| stranger-can-start | The plan's files or areas, its approach, and its order of work | Someone who has never seen the issue could start the work from the plan alone: it names the files, functions, or a specific code area where the change goes, and commits to one chosen approach. A named area with the exact function stated as an unknown to pin down during the build still passes. Fails if real decisions are left for later: no files or area named, "somewhere", "either X or Y, whichever is easier", "not sure which layer", or steps that only investigate, profile, or look into things and then "fix whatever turns up" | required |
| decisive-test | The plan's test plan, read against the repro evidence's steps and their shown output | The test plan names at least one specific observable result that the repro showed failing and that would be different after the fix (an exact output, exit code, status value, rendered state, or a named regression test of the repro case). Fails if the only success signal is a feeling or a non-event ("should feel fast", "nothing else should break", "should not panic anymore" with no expected result), or only "run the full test suite" with no check of this bug's behavior | required |
| thread-and-policy | The plan comment and plan, read against the thread highlights (direction from OWNER, MEMBER, or COLLABORATOR accounts, and open PRs) and against the repo-facts block's contribution policy | Passes only if both parts hold. (1) Thread: if a maintainer in the thread has named the culprit, given a direction, posted a patch or test build, or rejected an approach, or an open PR targets the same fix, the comment engages it (follows it, or says why it differs) instead of ignoring it or proposing what was rejected. If the thread has no such direction, this part passes. (2) Policy: if the contribution policy requires disclosing AI use in comments or in all contributions, the comment states that AI was used and how; treat every package as AI-assisted work. A policy that only asks contributors to understand and review AI output, or asks for disclosure only in the pull request, needs no disclosure in the comment. If no AI policy is stated, this part passes | required |
| unknowns-named | The plan's risks or unknowns, and any claim stated as certain in the plan or comment | Things the plan has not verified are stated as unknowns or risks instead of as fact. A plan with no risks section can still pass if it claims nothing beyond what the evidence shows | preferred |
| comment-matches-plan | The plan comment read against the plan | The comment describes the same cause, change, and scope as the plan, so a maintainer reading only the comment would expect the same work | preferred |

## Verdict rule

Accept if every required check passes. Reject if any required check
fails. An unclear grade on a required check counts as a fail, because a
plan I cannot verify from the package is not ready to build from.
Preferred checks never change the verdict, whatever their grade; they
only go in the summary as notes.
