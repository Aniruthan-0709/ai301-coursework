# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-matches-plan | Every file and hunk in the diff, read against the plan's scope (in scope, not in scope), its files list, its approach, and any deviation or deferral note in the plan | Every hunk in the diff does something the plan names or a deviation note explains, and every change the plan promises appears in the diff or is named as deferred in the plan or the description. Fails in either direction: the diff adds work the plan does not name (a refactor, a renaming pass, a new option, flag, or setting, an edit to a file the plan never mentions, or anything the plan lists as not in scope), or the diff leaves out a promised change with no note saying so. Regression tests for the planned fix count as in scope. A shortfall that the plan or the description names openly is not drift | required |
| description-matches-diff | Each claim in the PR title and description (what changed, which files, "exactly as planned", "no other changes", "docs updated", "adds a test"), read against the diff | Every claim the title and description make about the change is true of the diff, and the description does not hide a change a reviewer would need to know about. Fails if the description claims something the diff does not contain (docs, tests, a second fix), or claims fidelity ("implements the plan exactly", "no functional changes outside X") that the diff contradicts | required |
| repro-before-after | The test evidence section, read against the plan's test plan and the repro evidence the plan built on | The evidence re-runs the plan's repro (or the issue's repro) and shows an observable before and after: the failing output, status, or behavior before the fix and the expected-after result on the branch, for every failure case the plan's test plan names. Fails if the evidence is only a statement ("tested locally", "works now", "verified on my machine"), if it runs a different input or an unchanged path (a control case that never failed) instead of the failing case, or if it skips a failure case the test plan named | required |
| repo-checks-run | The test evidence section and the Testing part of the description, read against the test or check commands that the repo facts, the PR template, or the plan name | The outcome of the repo's own test suite or checks is shown, with the command named (for example "`cargo test -p ignore` passes (214 tests)"). A check that fails or cannot run passes this check only if the evidence says so plainly and gives the reason. Fails if the repo or the plan names a test command and the evidence never shows its result, or if a template box is ticked for a check the evidence does not show. If neither the repo nor the plan names any check, this check passes | required |
| no-debris | Every hunk in the diff and the commit list | The diff contains only the change and its tests. Fails if any hunk holds debug output (prints, eprintln, console.log, debug logging added for the session), commented-out code or earlier attempts, dead or unused functions, new TODO or FIXME notes, pure formatting or re-indent churn, import reshuffles, or whole blocks of unchanged lines removed and re-added with no change, even when the fix itself is correct. Unchanged lines that the diff shows as removed and re-added inside the statement the fix edits (for example the opening line of a call whose argument changed) are how diffs display that edit, not churn | required |
| template-and-repo-asks | The repo facts block's pull request asks (template sections, checklist items, issue link, changelog or release-note entry, title convention) and contribution guide, read against the description and the diff | Every ask the repo states for a pull request is met. Template sections are present and filled with real content, the issue is linked in the form the repo asks for (such as "Closes #123"), and any required file entry (CHANGELOG, whatsnew, release note) is in the diff. Fails if a required section, checklist, issue link, or required entry is missing or left as boilerplate. A section marked "N/A" with a reason counts as filled. If the repo states no pull request asks, this check passes | required |
| ai-disclosure | The repo facts block's contribution or AI policy, read against the PR description | Treat every package as AI-assisted work. If the repo's policy requires disclosing AI use in pull requests or in all contributions, the description states that AI was used, which tool, and how much of the work it did, in the author's own words. Fails if the policy requires disclosure and the description has none, or has only a boilerplate line that names no tool or extent. If the repo states no AI policy, or its policy asks only that contributors understand AI output, this check passes. In live mode, the course's rule counts as a stated policy: the description must disclose AI use under Notes for Reviewers | required |
| thread-direction-engaged | The issue's thread highlights (direction from maintainers, rejected approaches, open PRs on the same fix), read against the description | If a maintainer gave a direction, named a constraint, or rejected an approach, or another open PR targets the same fix, the description follows it or says why it differs. If the thread has none of these, this check passes | preferred |
| reviewer-can-follow | The title and the description's summary | A reviewer who has not read the issue can tell from the title and summary what bug is fixed and how, in a sentence or two, before opening the diff | preferred |

## Verdict rule

Accept if every required check passes. Reject if any required check
fails. An `unclear` grade on a required check counts as a fail,
because a PR I cannot verify from the package is not ready to submit.
Preferred checks never change the verdict, whatever their grade; they
go in the summary as notes only.

Less than everything is not a fail on its own. A PR that leaves part
of the plan out, or needed a change the plan did not name, passes
diff-matches-plan and description-matches-diff when the plan's
deviation notes or the description say so plainly. Grade what was
disclosed against what the diff does.
