# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| maintainer-active | Last 5 default-branch commits, and the maintainer first-response sample, in the repo-facts block | A human maintainer/collaborator (not a bot) merged a non-dependency-bump PR, or commented on an issue, within the last 60 days | required |
| repo-shipping | Latest release date, and the last 5 default-branch commits, in the repo-facts block | At least 1 release in the last 12 months, OR - if there is no release history - at least 3 of the last 5 default-branch commits (whether merged via a pull request or pushed directly) landed within the last 30 days, showing the project is under active, ongoing development without formal releases | required |
| bounded-scope | Issue title, description, and comment thread | Issue is not explicitly framed as a tracking/epic/meta issue meant to be split across multiple separate contributors or PRs (a single request that touches several related files or sub-steps as part of one cohesive, already-decided change is NOT an umbrella issue merely for having multiple parts). Its design is not still under open maintainer debate, and no maintainer has stated the fix touches core internals. A terse bug report, or a request with several concrete, already-decided sub-steps, can still pass - especially when opened by a maintainer/collaborator with a fleshed-out plan, or labeled good-first-issue; grade the size of the work asked for, not its length or polish. Fails on: pure usage/support questions; issues where the reporter's OWN wording admits genuine unresolved uncertainty about the object or approach itself (e.g. an asset explicitly marked "TBD", or wiring described as "possibly needed" with no decided answer) - as distinct from an issue that simply names multiple known root causes or lists optional/lower-priority nice-to-haves alongside a concrete core fix; or issues with a history of multiple (two or more) abandoned attempts (closed, unmerged PRs) signaling real difficulty | required |
| unclaimed | Repo-facts "assignees" and "linked PRs" fields, plus a scan of the comment thread for any PR number mentions | No assignee, and no OPEN PR (formally linked or only mentioned in the comment thread) referencing this issue number. A closed/unmerged PR referencing the issue is an abandoned attempt and does NOT fail this check. No claim comment in the last 30 days either | required |
| policy-compatible | Contribution policy statement in the repo-facts block (usually from CONTRIBUTING.md) | Fails when the policy explicitly states it does not accept, prohibits, disallows, or otherwise forbids AI-generated or AI-assisted contributions - regardless of whether it uses the literal word "ban." Conditions (disclosure, personal understanding/testing requirements, human review) are terms to follow, not a fail. No stated policy passes | required |

## Verdict rule

Accept only if all required checks pass. Any required check that fails, or comes back `unclear`, rejects the issue (unclear counts as fail - there are no preferred checks in this rubric, so nothing here affects ranking beyond the accept/reject line itself).
